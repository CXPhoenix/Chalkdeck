## Context

Spec 0002 Testing Decisions and ADR-0006. The checker has its own output contract, which is new
behaviour, so the checker itself is built with the normal `/tdd` loop (red → green). The content it
pins is characterized from V, and each content property's red evidence is a mutation (ADR-0006).
V is the T-0002 commit recorded in that ticket's Comments.

Branch `tickets/T-0003/style-skill-checker` from `main` after T-0002 has landed, in a worktree
outside the main checkout.

## Deliverable

`python3 scripts/check_style_skills.py` reports, with one line per violation, any drift of the five
Claude copies from their pinned protected content, and exits 0 on the tree at V. Its tests run in the
project's unittest command, and `AGENTS.md` and `tune-skills` point at it so later re-tunes see it.

## Acceptance criteria

1. **Output contract (normal TDD).** For each violation the checker prints
   `FAIL: <check id>: <repo-relative path>[:<line>]: <detail>` to stderr and exits 1; with none it
   prints one `PASS:` line to stdout and exits 0. Check ids: `K1` … `K13`, `DESC`, `BODY`, `LINK`,
   `MODEL`. Tests for this contract were red (assertion failures) before the implementation.
2. **Extraction rules** (written in the checker's docstring and the test plan table):
   - **Rule IDs (K1)**: matches of `\b(takahashi|jobs|wangxing|gates)\.[a-z][a-z_]*\b`, collected
     **per file** for every file of each style skill, so removing an ID from one `SKILL.md` fails
     even if references still contain it.
   - **Classification (K2)**: core = IDs on lines of `references/core-rule.md` matching
     `(?i)\brule id:`; adjustable = IDs on lines of `references/adjustments.md` matching
     `^\s*-\s*ID:`. Both sets compared per skill. The test plan confirms neither set is empty for any
     of the four style skills at V.
   - **Field names (K3)**: per file presence of each of `style_id`, `core_rules`,
     `adjustable_rules`, `rule_id`, `constraint`, for all five skills including the router.
   - **Protected sentences (K4–K6, K8, K10, K11)**: each listed with its file and its enclosing `##`
     heading; matched after collapsing every whitespace run (including line breaks) to one space;
     must appear under the same heading. The list also contains the router's stopping sentence "An
     honest limitation report completes this branch without settings." For `wangxing-style`, the
     string `張忘形` must remain in the frontmatter description (checked there, not under a heading).
   - **Byte-equal files (K7, K9, K12)**: SHA-256 of every file under `references/` of all five; K9
     additionally lists every URL in each `core-rule.md`.
   - **Frontmatter (K13)**: keys exactly `name` and `description`; `name` equals V.
   - **DESC**: applies only when the description differs from V; then the AC5 rules on the parsed
     YAML value, with the pronoun pattern `\b(I|me|my|you|your|we|our)\b` matched case-sensitively
     for `I` and case-insensitively for the rest, the first whitespace-delimited token stripped of
     punctuation matching `^[A-Z][a-z]+s$`, and every style name and alias present at V still present.
   - **BODY**: fewer than 500 lines after the frontmatter.
   - **LINK**: inline links `[text](target)` found across line breaks; targets resolved relative to
     the containing file, `#fragment` stripped, URLs skipped; YAML path strings in `styles.md` are not
     links (they are K7).
   - **MODEL**: case-sensitive `\b(Opus|Sonnet|Haiku|Fable|Mythos)\b`, `\bGPT-?\d`, and
     `\bclaude-[a-z]+-\d` absent unless present at V.
3. **Baseline** `scripts/style-skills-baseline.json` has `generated_from` = V's SHA,
   `approved_changes: []`, and the data above. It is generated by `--generate-baseline` from the
   tree at V; the baseline of record is the version in the commit that first adds it, whose SHA is
   written in Comments.
4. **Author approvals before tests are written**: the test plan table (every property and its
   mutation) and the protected-sentence list, both recorded in Comments with the author's words.
5. **Mutation evidence (ADR-0006)**: for every property in item 2, plus K13 and the
   `approved_changes` path (an approved change is checked against its approved text), a fixture copy
   built in a temporary directory outside the repository fails that property's test. The run log in
   Comments shows the commit SHA it ran at and repo-relative paths only.
6. **No fixtures in the repository** that mimic a `.claude/skills/<name>/` layout; the real skill
   files are never modified by tests.
7. **Discoverability.** `AGENTS.md` "Build and test commands" lists the checker. Both trees'
   `tune-skills/SKILL.md` keep lists gain one line: the style-skill baseline and checker; run the
   checker before and after any re-tune. Recorded as a `local_adaptations.tune-skills` addition
   beginning "Both runtimes:".
8. At HEAD: the checker exits 0, `python3 scripts/verify-project.py` exits 0, and
   `python3 -m unittest discover -s scripts -p 'test_*.py'` passes.
9. Coverage report table in Comments at close.

## 給使用者（zh-TW）

這張票寫一支檢查程式 `scripts/check_style_skills.py`，把 5 個 style skill 不能變的內容固定下來，包括 rule ID、設定欄位、受保護的句子、references 檔案等。之後只要有人改動這些內容，它就會一行一行列出來並判定失敗。

開始寫測試之前，我會先給你兩份清單核准：test plan table，以及要保護的句子清單。檢查程式本身照一般 TDD 先 red 再 green；被保護的內容則用「故意破壞一份暫存複本，確認檢查抓得到」來證明有效。AGENTS.md 和 tune-skills 都會記下這支程式，以後重新調校時不會漏跑。
