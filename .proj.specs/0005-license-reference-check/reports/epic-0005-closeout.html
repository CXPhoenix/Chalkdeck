代價：這個結論放掉了什麼

  • verifier 與 GitHub 的渲染不一致。以 pandoc 代理實測，fence 收尾行帶 CR、巢狀 list marker、開頭沒有 | 的表格列、跨行的 refdef label，verifier 都判 PASS，渲染結果卻不同（#10）。其中 CRLF 寫法在 commit 時會被 .gitattributes 正規化掉（#16）。這些都要等 L1 的文法 epic 才會修。
  • CLI 層的缺口。verify() 在授權引用檢查之前就先讀 provenance 檔：FIFO 會卡住，頂層是陣列會 traceback。「provenance 讀不到時 notices 仍會檢查」只在函式層成立（OQ-6）。
  • committed state 不是每次都檢查。verifier 只看檔案系統，沒 commit 的目標檔也會通過（OQ-4）。
  • 流程問題重複出現。「實作跑在測試前」「整批先寫測試」出現了三次，其中一次是在 owner 已經裁決要改之後（#15）。
  • 成本。有紀錄的 subagent 用量約 3.34M tokens、26 個 agent；stage 1、2、4、5 沒有記錄（#17）。

這份報告沒有主張的事

  • GitHub 本身怎麼渲染這些寫法：所有渲染判斷都來自 pandoc 代理（#18）。
  • notices 與 provenance 的授權內容在法律上是否正確：verifier 只檢查引用是否指向存在的檔案。
  • Assets 列的路徑、holder 與 terms：它們寫在 code span 裡，verifier 不解析。
  • 「確認 0 個問題」只涵蓋這個 epic 的 diff，不代表整個專案是安全的。
  • retrospective.md 裡的改法只是提議，還沒經過你決定。
